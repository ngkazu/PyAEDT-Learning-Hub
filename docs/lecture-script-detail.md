## 1. イントロダクション（5分）

### 1.1 導入の語り口

「今日はPyAEDTというツールを使って、Ansys Electronics Desktop、略してAEDTをPythonから自動操作する方法を
学びます。普段AEDTをGUIで操作している方は、まず『同じことがコードでできる』という感覚をつかんでください。
Pythonに慣れている方は、今日の内容はごく普通のPythonのクラス・メソッド呼び出しの延長線上にあることが
すぐわかると思います。」

### 1.2 PyAEDTとは何か（丁寧な説明）

PyAEDTは、`ansys.aedt.core` という名前でインストールされる、Ansysの公式Pythonライブラリです。
AEDTは単一のソフトウェアではなく、HFSS（高周波電磁界解析）、Maxwell（低周波電磁界解析）、
Icepak（熱流体解析）、Q3D Extractor（寄生成分抽出）、Circuit（回路シミュレーション）など、
物理現象ごとに異なる解析エンジン（ソルバー）をまとめたプラットフォームです。PyAEDTは、
これらすべてのソルバーに対して「同じ流儀」でアクセスできるようにする統一的なAPIを提供します。

具体的に言うと、AEDTのGUIで「モデルを作る」「材料を設定する」「境界条件を割り当てる」
「メッシュを切る」「解析を実行する」「結果を見る」という一連の作業は、すべてPyAEDTの
Pythonオブジェクトのメソッド呼び出しとして表現できます。GUIで3時間かかる試行錯誤を、
一度スクリプトに落とし込んでしまえば、何度でも数分で再現できるようになります。

もう一つ触れておきたいのは、レイアウト・基板（ECAD）の世界を扱う **PyEDB**（`pyedb`）という
別パッケージの存在です。HFSS 3D LayoutやEDB（Electronics Database）を直接操作したい場合は
PyEDBを使います。PyAEDTとPyEDBは密接に連携しますが、パッケージとしては別物です。今日の講義では
PyAEDT本体に集中し、PyEDBには深入りしません。

### 1.3 なぜPyAEDTを使うのか（動機づけ）

ここは聴衆の「なぜGUIじゃダメなのか」という疑問に答える部分なので、具体例を交えてゆっくり話す。

1つ目の理由は**再現性**です。GUIでの操作は、同じ手順を人間が再現しようとすると、クリックの順番や
入力値の打ち間違いなど、微妙なブレが生じがちです。スクリプトに書いてしまえば、同じコードは何度実行しても
同じ結果を生みます。チームで設計レビューをするときも、「このスクリプトを実行すればこのモデルが再現できる」
という状態は非常に強力です。

2つ目は**パラメトリックスタディ**のしやすさです。「アンテナの長さを1mm刻みで10パターン試して、
それぞれの共振周波数を比較したい」というようなタスクは、GUIで10回繰り返すよりも、Pythonのfor文で
回したほうが圧倒的に速く、ミスも減ります。

3つ目は、Pythonの**通常のエコシステム**と組み合わせられる点です。解析結果をnumpyの配列として取得し、
pandasでデータフレームに整形し、matplotlibでグラフにする、といった一般的なデータ処理の技術が
そのまま使えます。これは、あとで第3節・第4節でも繰り返し出てくるテーマです。

4つ目は、AEDTに内蔵されているスクリプト機能（IronPython・VBScriptベース）との違いです。
内蔵スクリプトはAEDTのプロセス内でしか動かない特殊な実行環境ですが、PyAEDTは普通のCPython、
つまり皆さんが普段使っているのと同じPythonインタープリタで動きます。そのため、VS Codeのような
普通のIDE、pdbやdebugpyによる通常のデバッガ、pytestのようなテストフレームワーク、
仮想環境（venv）によるパッケージ管理など、通常のPython開発で当たり前に使う道具立てが
そのまま使えます。この違いは第4節で詳しく扱います。

### 1.4 このあとの流れ

「このあと第2節でPyAEDTの基本構造を見て、第3節で実際にAEDTを操作するデモをお見せします。
第4節では、AEDTのGUI操作を記録してコード化する機能と、PyAEDTのコードがどう対応するかを

## 2. PyAEDTの基本構造（15分）

### 2.1 パッケージ全体像

```python
from ansys.aedt.core import Hfss, Icepak, Maxwell3d, Q3d, Circuit
```

まず最初に伝えたいのは、`ansys.aedt.core` というパッケージの直下に、AEDTの各アプリケーションに
対応するクラスが1つずつ用意されている、という事実です。HFSSを使いたければ `Hfss` クラス、
Maxwell 3Dを使いたければ `Maxwell3d` クラス、という具合です。クラス名の綴りがアプリの表示名と
微妙に違う場合がある点（例えば2D Extractorは `Q2d`、IcepakFEAは `Mechanical`）には注意が必要です。
今日扱う全アプリとクラス名の対応表は [docs/app-selection.md](app-selection.md) に一覧化してあるので、
迷ったらそこを見てください。この表は演習の `starter.py` を書くときにも繰り返し参照することになります。

### 2.2 「アプリオブジェクト」を起点にすべてが決まる

PyAEDTのコードは、ほぼ例外なく次のパターンで始まります。

```python
hfss = Hfss(version="2026.1", new_desktop=True, non_graphical=False)
```

この1行が実行された瞬間に、裏側ではAEDTのプロセスが起動（または既存プロセスへの接続）し、
新しいプロジェクト・デザインが作成されます。戻り値の `hfss` という変数（これを「アプリオブジェクト」と
呼ぶことにします）が、以降のすべての操作の起点になります。

3つの引数それぞれについて、ゆっくり説明します。

- `version`: 使用するAEDTのバージョンを文字列で指定します。複数バージョンのAEDTが同じマシンに
  入っていることもあるので、明示しておくと安全です。手元の環境のバージョンは、AEDTを起動して
  「ヘルプ > バージョン情報」で確認できます（詳細は
  [lecture/00_environment_setup.md](../lecture/00_environment_setup.md)）。
- `new_desktop`: `True` にすると、新しいAEDTプロセスを起動します。`False` にすると、
  既に起動しているAEDTセッションに接続しにいきます（`port` や `aedt_process_id` を併用して
  どのプロセスに繋ぐか指定することもできます）。この違いは地味に重要で、何も考えずに
  `new_desktop=True` のスクリプトを繰り返し実行すると、AEDTプロセスがどんどん増えてしまいます。
- `non_graphical`: `True` にすると画面を一切出さずバックグラウンドで動作します。CI（継続的インテグレーション）
  環境や、バッチ処理でたくさんのケースを流したいときに使います。今日のデモでは、画面を見せながら
  説明したいので `False` にしています。

「この `hfss` という1つのオブジェクトが、これから話すすべての機能の入り口になります」という点を
強調しておくと、次の2.3節への接続がスムーズです。

### 2.3 主なサブオブジェクト

アプリオブジェクトは、役割ごとに整理されたサブオブジェクトをプロパティとして持っています。
表にまとめると次のようになります（実際に話すときは、1行ずつ具体例を交えて説明する）。

| プロパティ | 役割 | 話すときの具体例 |
|---|---|---|
| `hfss.modeler` | 形状（ジオメトリ）の作成・変更 | 「箱を作る、円柱を作る、ブーリアン演算で結合・削除する、といった3D/2Dモデリングはすべてここ」 |
| `hfss.materials` | 物性（材料）の作成・変更 | 「銅や空気といった既存材料を使うだけでなく、独自の導電率・透磁率を持つカスタム材料もここで作れる」 |
| `hfss.boundaries` | 境界条件・励振の一覧・追加 | 「ポート、電流源、完全導体境界など、物理的な境界条件の管理はここ」 |
| `hfss.mesh` | メッシュ設定 | 「メッシュの細分化領域の指定など」 |
| `hfss.setups` / `hfss.create_setup(...)` | 解析Setup（周波数・収束条件など）の作成 | 「GUIの『Analysis』ツリーに相当する部分」 |
| `hfss.post` | 結果のポスト処理 | 「レポート作成、フィールドプロット、ソリューションデータの取得など、解析結果に関する操作は全部ここに集まっている」 |
| `hfss.odesktop` / `hfss.oproject` / `hfss.odesign` / `hfss.oeditor` | AEDTのネイティブAPI（COMオブジェクト）への直接アクセス | 「これは第4節でじっくり説明します。ここでは『抜け道として存在する』とだけ覚えておいてください」 |

ここで強調したいポイントは、「どのアプリクラス（`Hfss` / `Icepak` / `Maxwell3d` など）でも、
この構造はほぼ共通している」ということです。`modeler` で形を作り、`materials` で物性を決め、
境界条件を割り当て、`create_setup` で解析条件を作り、`post` で結果を見る。この5ステップの流れは、
今日扱うどのアプリでも変わりません。アプリ固有の機能（例えばMaxwellの`assign_coil`や
Q3Dの`insert_reduced_matrix`のような）は、この共通構造の上に追加のメソッドとして乗っているだけです。
この「共通構造＋アプリ固有の拡張」という見方ができると、新しいアプリを触るときの心理的ハードルが
かなり下がります。

> オブジェクト階層・接続モデル、変数システム、各サブオブジェクトの内部クラス構造をもう一段深く
> 知りたい場合は [lecture/03_pyaedt_architecture.md](../lecture/03_pyaedt_architecture.md) を参照（任意）。

### 2.4 APIの調べ方（推測しない、という姿勢の共有）

「このあと演習を進めていく中で、必ず『このメソッドの引数は何を渡せばいいんだろう』と迷う場面が
出てきます。そのときにどう調べるかを、最初に共有しておきます。」

1. まず試してほしいのは、Python標準の `dir(obj)` と `help(obj.method)` です。`dir(hfss.modeler)` と
   打てば、`modeler` オブジェクトが持っているメソッド・プロパティの一覧がその場で見られます。
   `help(hfss.modeler.create_box)` と打てば、docstring（説明文）がその場で表示されます。
   これは今日これから使うインタラクティブな環境（Pythonの対話シェルやJupyter、VS Codeの
   デバッグコンソールなど）でそのまま使えます。
2. 次に、公式ドキュメント（https://aedt.docs.pyansys.com/）も当然参照できますが、
   情報が古かったりバージョン間の差異が反映しきれていなかったりすることもあります。
3. 一番確実なのは、PyAEDTパッケージ本体のソースコードを直接読むことです。`pip install` された
   場所、あるいはこのプロジェクトが使っているようにGitHubからクローンしたローカルリポジトリを
   grepすれば、引数名・デフォルト値・内部実装まですべて正確にわかります。

「推測で書いたコードはだいたい動かないか、動いても意図と違う挙動をします。迷ったら調べる、
という姿勢をこの講義の最初に共有しておきたいと思います。実際、このプロジェクトの演習教材自体も、
この3つの方法で裏取りしながら作っています。」

## 3. 基本操作デモ（15分）

ここは実際に画面を見せながら進める。読み上げる内容は「次に何をするか」の説明と、
コードを実行した直後に画面で何が起きるかの実況が中心になる。

### 3.1 デモの流れの予告

「ここからは実際に手を動かします。やることはシンプルで、『AEDTを起動する → 箱を1つ作る →
保存する → 終了する』という、考えうる限り最小の一連の流れです。地味に見えるかもしれませんが、
この4ステップのパターンは、今日この後の演習、そして実務で書くどんなスクリプトでも必ず現れる
『型』です。」

`demo/demo1_basic_operations.py` を開いて、上から順に実行しながら説明する。

```python
from ansys.aedt.core import Hfss

# 1. 起動（新規プロジェクトでHFSSを開く）
hfss = Hfss(version="2026.1", new_desktop=True, non_graphical=False)

# 2. 変数を定義する
hfss["box_size"] = "10mm"

# 3. 箱を作る（形状作成）
hfss.modeler.create_box(
    origin=[0, 0, 0],
    sizes=["box_size", "box_size", "box_size"],
    name="Box1",
    material="vacuum",
)

# 4. 保存する
hfss.save_project()

# 5. 終了する（AEDTプロセスとプロジェクトを閉じる）
hfss.release_desktop(close_projects=True, close_desktop=True)
```

### 3.2 各ステップの詳しい解説

**起動**（1行目〜）: 実行するとAEDTのウィンドウが開く。「ここで少し待ち時間が発生します。
AEDTというアプリケーション自体の起動に数秒〜数十秒かかるためで、PyAEDT固有の遅さではありません。」

**変数定義**（`hfss["box_size"] = "10mm"`）: ここは特に時間をかけて説明する価値がある。
「角括弧を使ったこの書き方は、Pythonの辞書のように見えますが、実際にはAEDTの**設計変数**
（デザインプロパティ）として登録されます。GUIの『Properties』パネルの変数一覧に、
`box_size = 10mm` という項目が実際に追加されるのを確認してください。重要なのは、
この変数は単なるPython変数ではなく、AEDT側に実体を持つという点です。あとでGUIから値を変更すれば、
形状がリアルタイムに追従します。」

**形状作成**（`create_box`）: 「`sizes` に `box_size` という文字列を渡している点に注目してください。
数値の `10` を直接渡すこともできますが、ここでは変数名の文字列を渡すことで、AEDT側の変数参照の
式（expression）として評価されます。これにより、あとで `box_size` の値を変えるだけで
箱のサイズが連動して変わる、パラメトリックなモデルになります。」ここで実際にGUIの3Dビューに
切り替えて、箱が生成されているのを見せる。

**保存**（`save_project`）: 「このタイミングで `.aedt` ファイルがディスクに書き出されます。」

**終了**（`release_desktop`）: ここは強調して注意喚起する。「このメソッドを呼ばずにスクリプトを
終了させてしまうと、AEDTのプロセスがバックグラウンドに残り続けます。残り続けると何が困るかというと、
(1) 次にスクリプトを実行したときに意図せず既存プロセスに接続してしまったり、(2) AEDTのライセンスを
掴んだままになって他の利用者や自分自身の次回起動をブロックしてしまったり、といった問題が起こります。
`close_projects=True, close_desktop=True` を付けて、プロジェクトとデスクトップの両方を
きちんと閉じる習慣をつけてください。」

### 3.3 つまずきやすいポイントの先回り

「演習を自分でやってみると、次のような場面でつまずきやすいので、先に共有しておきます。」

- スクリプトを途中で止めてしまった（例外が発生した、Ctrl+Cで止めた）場合、AEDTプロセスが
  残ることがあります。`settings.release_on_exception = False`
  （[lecture/00_environment_setup.md](../lecture/00_environment_setup.md)参照）を
  設定しておくと、例外発生時にAEDTが自動終了してしまうのを防げるので、原因調査がしやすくなります。
- `non_graphical=False` で動かしている間は、AEDTのウィンドウが実際に操作可能な状態になっています。
  うっかり手動でクリックしてしまうと、スクリプトの実行と手動操作が競合することがあるので注意してください。

## 4. AEDT内蔵Script → PyAEDT変換（8分）

### 4.1 なぜこの節が必要か

「ここまでは最初からPyAEDTで書く前提で話してきましたが、実務ではもう1つのパターンがよく出てきます。
『まずGUIで試行錯誤して形を作り、その後で自動化したい』というパターンです。AEDTにはGUI操作を
スクリプトとして記録する機能が内蔵されており、この節ではその出力とPyAEDTのコードがどう対応するかを
説明します。」

### 4.2 AEDTのスクリプト記録機能

AEDTのメニューから、GUI操作をIronPython（Python 2系の文法に近い、.NET上で動くPython実装）または
VBScript形式のコードとして書き出す機能が使えます。記録されたコードは、`oDesktop` / `oProject` /
`oDesign` / `oEditor` という名前の特殊なオブジェクトに対して、AEDTのネイティブAPI（内部的には
COMベースのインターフェース）のメソッドを直接呼び出す形になっています。

`demo/demo2_before_native_script.py` を見せながら説明する。実際に記録される内容を簡略化した例が
次のコードです。

```python
# AEDT内蔵スクリプト記録が出力するコードのイメージ（簡略化）
oDesktop.RestoreWindow()
oProject = oDesktop.SetActiveProject("Project1")
oDesign = oProject.SetActiveDesign("HFSSDesign1")
oEditor = oDesign.SetActiveEditor("3D Modeler")
oEditor.CreateBox(
    [
        "NAME:BoxParameters",
        "XPosition:=", "0mm",
        "YPosition:=", "0mm",
        "ZPosition:=", "0mm",
        "XSize:=", "10mm",
        "YSize:=", "10mm",
        "ZSize:=", "10mm",
    ],
    [
        "NAME:Attributes",
        "Name:=", "Box1",
        "Flags:=", "",
        "Color:=", "(143 175 143)",
        "Transparency:=", 0,
        "PartCoordinateSystem:=", "Global",
        "UDMId:=", "",
        "MaterialValue:=", "\"vacuum\"",
        "SurfaceMaterialValue:=", "\"\"",
        "SolveInside:=", True,
    ],
)
```

「このコードの特徴を2つ指摘しておきます。1つ目は、引数が `\"NAME:BoxParameters\", [...]\"` のような、
AEDTのネイティブAPI特有のキーと値を交互に並べたリスト形式になっている点です。これはPythonらしい
書き方ではなく、COM APIをそのままPythonの構文に当てはめたものです。2つ目は、このコードは
`oDesktop` 等の変数が最初から用意されている前提で書かれているため、**このコードだけを別のPython
環境にコピーしても動かない**という点です。AEDTのスクリプトコンソールの中でだけ完結するコードです。」

### 4.3 変換方法（2つのアプローチ）

ここが今日の山場の1つなので、ゆっくり、対比をはっきりさせながら話す。

**(a) 橋渡し方式**: PyAEDTのアプリオブジェクトは、先ほど2.3節の表で触れた
`.odesktop` / `.oproject` / `.odesign` / `.oeditor` というプロパティを通じて、まったく同じ
ネイティブAPIオブジェクトを公開しています。つまり、記録されたコードの `oEditor.CreateBox(...)` の
部分を `hfss.oeditor.CreateBox(...)` に書き換えるだけで、そのままPythonスクリプトとして動かせます。
`demo/demo2_after_pyaedt_conversion.py` の前半部分がこの例です。

```python
# (a) 橋渡し方式: 記録スクリプトの oEditor.CreateBox(...) を app.oeditor.CreateBox(...) に置き換えるだけ
hfss.oeditor.CreateBox(
    [
        "NAME:BoxParameters",
        "XPosition:=", "0mm",
        "YPosition:=", "0mm",
        "ZPosition:=", "0mm",
        "XSize:=", "10mm",
        "YSize:=", "10mm",
        "ZSize:=", "10mm",
    ],
    [
        "NAME:Attributes",
        "Name:=", "Box1",
        "Flags:=", "",
        "Color:=", "(143 175 143)",
        "Transparency:=", 0,
        "PartCoordinateSystem:=", "Global",
        "UDMId:=", "",
        "MaterialValue:=", "\"vacuum\"",
        "SurfaceMaterialValue:=", "\"\"",
        "SolveInside:=", True,
    ],
)
```

「このアプローチの良いところは、**ほぼ機械的な置き換えだけで動く**という速さです。
GUIで作った複雑な形状（何十個もの引数を持つような複雑なフィーチャー）を、短時間で
『とにかく動くPythonスクリプト』にしたいときに向いています。欠点は、コードの意図が読み取りにくい
（`\"XPosition:=\", \"0mm\"` が何を表しているか、慣れないと分かりにくい）ことと、
引数リストの構造をAEDT側の仕様に合わせて正確に保たなければならない点です。」

**(b) 高レベルAPIへの書き直し（推奨）**: 第3節で見た `hfss.modeler.create_box(origin=...,
sizes=..., name=..., material=...)` のような、PyAEDTが提供する高レベルなAPIに書き直す方法です。

```python
# (b) 高レベルAPI方式（推奨）: 同じ箱を PyAEDT の modeler API で作成
hfss.modeler.create_box(
    origin=[20, 0, 0],
    sizes=[10, 10, 10],
    name="Box2",
    material="vacuum",
)
```

「見比べてみると一目瞭然ですが、`create_box` のほうが、引数名（`origin`, `sizes`, `name`, `material`）
から何をしているのかが明確に読み取れます。こちらのアプローチの良いところは、**保守性・可読性**です。
半年後に自分や同僚がこのコードを読んだときに、意図がすぐ分かります。また、`modeler.create_box`
という書き方は、Hfssに限らずMaxwell3dでもIcepakでも（Maxwell固有・Icepak固有の違いはあれど）
同じような流儀で使えるため、**他のアプリへの応用が効く**という利点もあります。」

### 4.4 使い分けの指針

「結論としては、新規にコードを書くときは基本的に(b)の高レベルAPIを使ってください。(a)の橋渡し方式は、
GUIで既に作り込んだ複雑な形状を『取り急ぎ移植したい』という限定的な場面で、一時的な手段として
使うのが実務的です。このプロジェクトの演習教材も、すべて(b)の高レベルAPIで書かれています。」
